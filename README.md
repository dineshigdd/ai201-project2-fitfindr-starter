## Tool Inventory

This section details the custom toolset implemented for FitFind. Each tool features a strictly defined interface to ensure seamless data flow and predictable state management within the agent loop.

### 1. `search_listings`
* **Purpose:** Searches the mock fashion database to locate clothing and accessory items that match a user's textual description, filtering dynamically by size and maximum price constraints.
* **Inputs:**
  * `description` (`str`): The keyword search query extracted from the user's prompt (e.g., `"vintage graphic tee"`).
  * `size` (`str` or `None`): The requested garment size (e.g., `"M"`). If `None`, the size filtering constraint is skipped gracefully.
  * `max_price` (`float` or `None`): The maximum upper budget boundary for the item. If `None`, the price filtering constraint is skipped gracefully.
* **Outputs:** `list[dict]`
  * Returns an array of dictionary objects representing matching product items sorted by relevance. 
  * *Failure Mode:* If zero items match the criteria, it safely returns an empty list (`[]`) instead of raising a Python exception.

---

### 2. `suggest_outfit`
* **Purpose:** Leverages the Groq LLM to generate creative, personalized styling combinations by evaluating a newly discovered listing against the items present in the user's current wardrobe.
* **Inputs:**
  * `new_item` (`dict`): The specific product dictionary selected as the top match from the search results.
  * `wardrobe` (`dict`): A structured dictionary mapping out the user's available clothing collection (matching the `wardrobe_schema.json` format).
* **Outputs:** `str`
  * Returns a natural language string containing actionable advice on outfit combinations, layering choices, and overall aesthetic styling.
  * *Failure Mode:* If the user's wardrobe is empty or minimal, the tool handles it cleanly by generating broad, standalone styling advice for the item rather than crashing.

---

### 3. `create_fit_card`
* **Purpose:** Generates a short, high-energy, shareable social media caption showcasing the completed outfit selection.
* **Inputs:**
  * `outfit` (`str`): The textual styling recommendation string generated by `suggest_outfit`.
  * `new_item` (`dict`): The product dictionary representing the newly found item.
* **Outputs:** `str`
  * Returns a short (≤ 2 sentence, ~30 word) casual, authentic-sounding social media caption tailored for an Instagram/TikTok post — mentioning the item name, price, and platform once each.
  * *Failure Mode:* If passed an empty outfit string or an incomplete input, it halts execution and returns a safe, clean fallback string error message rather than throwing a Python exception.

## Planning Loop Explanation

The core orchestrator of FitFindr is a centralized planning loop implemented inside `agent.py` via the `run_agent()` entry point. Instead of forcing a rigid, unyielding pipeline execution, the agent evaluates the execution status and output structural state after every single operation. If a dependency constraint or data boundary fails, the agent intercepts the sequence, sets an informative error status, and alters its execution route gracefully.

### Sequential Processing and Dynamic Branching Logic

```mermaid
graph TD
    A[User Raw Query] --> B(Step 1: Initialize Fresh Session Dict)
    B --> C(Step 2: LLM Query Parsing via Groq)
    C -->|Extraction Fails / No Description| D[Halt Loop: Return Understanding Error]
    C -->|Success: Structured Schema| E(Step 3: search_listings Execution)
    E -->|Empty Array Returned '[]'| F[Halt Loop: Return No-Results Error]
    E -->|Populated Array Returned| G(Step 4: State Management Selection)
    G --> H(Step 5: suggest_outfit Execution)
    H -->|Tool Error Caught / Empty| I[Halt Loop: Return Styling Failure Message]
    H -->|Success: Styling Advice String| J(Step 6: create_fit_card Execution)
    J -->|Tool Error Caught / Empty| K[Halt Loop: Return Fit Card Error Message]
    J -->|Success: Caption String| L[Step 7: Success State Return]
```

## State Management Approach

FitFindr implements a **centralized, single-source-of-truth state management pattern** to handle data propagation across complex multi-tool execution environments. Rather than passing isolated parameters between disconnected tools, all operational context, database payloads, and intermediary LLM outputs are captured inside a mutable session dictionary initialized by `_new_session()`.

### The Centralized State Architecture

The lifecycle of a single user interaction is encapsulated entirely within the following structured state schema:

| Key | Data Type | Purpose | Upstream Creator | Downstream Consumer |
| :--- | :--- | :--- | :--- | :--- |
| `"query"` | `str` | Holds the raw, unaltered incoming string from the user. | System Input | `_parse_query()` |
| `"parsed"` | `dict` | Houses the structural `description`, `size`, and `max_price` fields. | `_parse_query()` | `search_listings()` |
| `"search_results"`| `list[dict]` | An array containing all filtered product records returned from storage. | `search_listings()` | Agent Selection Loop |
| `"selected_item"` | `dict` or `None`| The specific, top-ranked listing matching the description criteria. | Agent Selection Loop | `suggest_outfit()`, `create_fit_card()` |
| `"wardrobe"` | `dict` | Structured collection matching `wardrobe_schema.json`. | System Input | `suggest_outfit()` |
| `"outfit_suggestion"`| `str` or `None`| Natural language styling advice returned by the Groq LLM. | `suggest_outfit()` | `create_fit_card()` |
| `"fit_card"` | `str` or `None`| Final shareable high-energy social media caption snippet. | `create_fit_card()` | Front-End Layout Display |
| `"error"` | `str` or `None`| Tracks the failure context string if the pipeline terminates early. | Tool Guard Interceptors | System Output Layer |

### Principles of State Mutation and Data Flow

1. **Decoupled Data Flow:** Downstream tools remain entirely agnostic of each other.  
    - For example, `create_fit_card()` does not know that `suggest_outfit()` exists or how it ran; it simply reads the string payload present at `session["outfit_suggestion"]`. This allows tools to be tested and updated in total isolation.

2. **Defensive Modification:** The central orchestrator inside `agent.py` acts as a strict gateway controller. Before any value is committed to a session state slot, it passes through data extraction sanitizers (like regex numeric check fallbacks in `_parse_query()`) or error string checkers (like `_is_tool_error()`).

3. **Idempotency and Resilience:** If a tool fails or an invalid state is reached, the state transitions directly to an error state (`session["error"] = "..."`) and stops execution. This ensures that a corrupted block of data cannot cascade down the line to pollute other state parameters or trigger unwanted LLM token expenses on broken inputs.

## Error Handling per Tool

### Tool 1: `search_listings`

#### Error Handling Strategy
The search tool handles failures defensively by ensuring that tight filtering constraints or unmatched keywords never disrupt the execution of the main program. 
* Rather than raising a `KeyError`, `IndexError`, or custom exception when no database records match the criteria, the tool gracefully intercepts the empty state and returns an empty list (`[]`). 
* This allows the upstream orchestrator (`agent.py`) to inspect the structural length of the output cleanly, register a friendly error message for the user, and halt downstream processing before invalid data enters the LLM pipelines.

#### Testing Example
During test execution, an impossible query was passed to evaluate this graceful exit path:

* **Test Input Query:** `"designer gown"` with `size="XXS"` and `max_price=5`.
* **Database Behavior:** The internal database filter scanner evaluated all items against the strict $5 price ceiling and `"XXS"` sizing parameters. Zero records matched these values, reducing the target array down to nothing.
* **Observed Test Outcome:** The function successfully caught the empty constraint match and returned `[]` cleanly without breaking. This was verified via `pytest` inside our automated test case:

```python
def test_search_impossible_returns_empty():
    results = search_listings("designer gown", size="XXS", max_price=5)
    assert results == []   # Verifies an empty list is returned with no exception raised
```

### Tool 2: `suggest_outfit`

#### Error Handling Strategy
The outfit suggestion tool operates defensively against two distinct failure modes—data deficiencies and external infrastructure collapses:
* **Empty User Wardrobes:** If the user's wardrobe list is completely empty, the tool intercepts the state early. Instead of crashing, returning an empty string, or hallucinating pieces the user doesn't own, it switches to an alternate prompt branch that directs the LLM to output broad, versatile styling paradigms.

* **API and Network Exceptions:** Because calling an external LLM provider can fail due to connection timeouts, rate limiting, or authentication errors, the tool wraps the client interaction within a comprehensive `try/except Exception` block. If the API errors out, the tool catches the exception cleanly and returns a warm, descriptive error string containing diagnostic information rather than allowing a fatal application crash.

#### Testing Example
To verify that the system handles a total breakdown of the LLM provider without crashing the program loop, a failure scenario was validated using a mock environment:

* **Test Configuration:** The internal client factory dependency (`_get_groq_client`) was deliberately patched using a mock utility function designed to immediately trigger a runtime exception.
* **Simulated Behavior:** When `suggest_outfit` executes, it encounters the rigged connection wrapper which instantly raises `Exception("LLM API failure")`.
* **Observed Test Outcome:** The function successfully caught the exception internally, suppressed the application crash, and returned a user-facing error message string. This recovery mechanism is actively verified via our automated test suite:


```python
#in test_suggest_outfit_tool.py
def test_suggest_outfit_llm_failure(monkeypatch):
    def boom():
        raise Exception("LLM API failure")

    # Force the internal factory to crash on call
    monkeypatch.setattr(tools, "_get_groq_client", boom)

    # Execute the function — must catch the crash internally
    result = suggest_outfit(NEW_ITEM, POPULATED_WARDROBE)

    assert isinstance(result, str)
    assert "sorry" in result.lower() or "problem" in result.lower()
```

### Tool 3: `create_fit_card`

#### Error Handling Strategy
The shareable fit card tool employs two defensive validation layers to guarantee system stability and optimize API resource consumption:
* **Pre-Execution Input Guards:** Before triggering any external infrastructure pipelines, the tool evaluates the incoming `outfit` suggestion string. If it discovers an empty string or whitespace-only buffer (`"   "`), it intercepts the flow immediately. Rather than forwarding corrupted or blank context blocks downstream to the LLM (which would result in an expensive, hallucinated, or broken caption response), it bypasses the network completely and returns a clean, hardcoded diagnostic error string.

* **API and Network Exceptions:** To protect the main orchestrator loop against network disconnects, rate limits, or bad credentials during text generation, the LLM client call is wrapped inside a robust `try/except Exception` block. If the connection fails, the tool extracts the class name of the exception, appends it to a human-readable mitigation message, and returns it safely to prevent a fatal application crash.

#### Concrete Testing Example
To verify that the pre-execution input guard blocks blank entries from hitting your API, you can look at the automated isolation tests inside our test suite:

```python
def test_create_fit_card_empty_outfit(monkeypatch):
    # If the LLM wrapper is reached, this rule triggers a total failure—
    # proving the validation guard intercepts execution BEFORE any client call.
    def explode():
        raise AssertionError("LLM should not be called for an empty outfit")

    monkeypatch.setattr(tools, "_get_groq_client", explode)

    # Confirm both completely empty and whitespace inputs return the error string safely
    assert create_fit_card("", NEW_ITEM) == "Sorry, I couldn't create a fit card for that outfit."
    assert create_fit_card("   ", NEW_ITEM) == "Sorry, I couldn't create a fit card for that outfit."
```
## Spec Reflection

### 1. How the Spec Helped
Drafting the technical specifications in `planning.md` was invaluable when implementing both the individual functions in `tools.py` and the core orchestration loop in `agent.py`. Mapping out the system upfront provided absolute clarity regarding parameter names, data types, strict return values, and error-handling boundaries. It also defined how data flows securely through session states and how each tool interacts dynamically within the architecture.

This comprehensive blueprint dramatically streamlined development when collaborating with AI coding tools. Because the specifications were so precise, I was able to feed isolated, highly contextual prompts into our development LLM. This eliminated guesswork, prevented context drift, and ensured that the generated tool skeletons perfectly matched our structural expectations on the very first try with minimal errors.

### 2. How the Implementation Diverged and Why
While the final code fundamentally mirrors the architecture laid out in `planning.md`, a few implementation details evolved beyond what the spec originally described:

**1. Query parsing became an explicit LLM step.**  
- `planning.md`'s planning loop begins at *"IF `session["parsed"]` is empty"* but never specified *how* the raw query becomes the structured `description` / `size` / `max_price`. During implementation I made this an explicit LLM call (`_parse_query()`, using Groq in JSON mode) rather than brittle regex or string-splitting. 
- Because the keyword scorer in `search_listings` is sensitive to filler words, so letting the model return a clean `description` (e.g. `"vintage graphic tee"` instead of `"looking for a vintage graphic tee under $30"`) keeps relevance scoring accurate. 
- This is the *"Step 2: LLM Query Parsing via Groq"* node in the diagram above.

**2. Orchestrator-level error interception (`_is_tool_error()`).** 
- While the final code matches the overall architecture from the spec, the implementation diverged when handling tool fallbacks. Originally, the spec assumed that downstream tools would natively handle all context-level issues. However, during testing, It is discovered that if `suggest_outfit` errors out, it actually returns a prose error string ("Sorry, I ran into a problem…") instead of raising an exception. If this error string is stored and passed along, it completely corrupts the input context for `create_fit_card`. 

- To fix this, a defensive orchestrator-level checker function, `_is_tool_error()` is added. This helper function catches these fallback error signatures directly inside the planning loop and triggers an early termination. This protects downstream tools from executing on bad or corrupted data— introducing a precise error-tracking workflow that wasn't planned in the initial specification.

**3. Defensive guard around `search_listings`.** 
- While the Tool 1 spec guarantees that `search_listings` never raises an exception (it just returns an empty list `[]` when there is no match), the planning loop still wraps the call in a `try/except` block as a backup safety measure. This ensures that if the data loading ever fails unexpectedly, the system will show a friendly error message instead of crashing with a stack trace. This specific branch is not part of the planned error table.

**4. Caption temperature.**
- `planning.md` suggested an elevated temperature *"e.g., 0.7 or 0.8"* for `create_fit_card`; the final code uses `0.9` (plus a `max_completion_tokens` cap) after testing showed slightly punchier, more varied captions without sacrificing coherence or length control.
